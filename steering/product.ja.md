## 製品ビジョン

### 私たちが構築するもの

**MUSUHI 2.0: AI支援コーディングのための汎用Specification Driven Development フレームワーク**

6つの主要SDDツールのベストプラクティスを組み合わせたプラットフォーム非依存のSDDオーケストレーションフレームワークで、8つの主要AIコーディングプラットフォーム全体で厳格で追跡可能、AI支援のソフトウェア開発を実現します。

MUSUHI 2.0は、開発チームがAIアシスタントと働く方法を変革します:

- **憲法原則の適用**: 9つの不変条項により、過剰設計を防止しベストプラクティスを保証
- **変更の厳格な管理**: 2フォルダーモデル（specs/ + changes/）でブラウンフィールドプロジェクトをサポート
- **マルチエージェントワークフローのオーケストレーション**: 20の専門AIエージェントがシームレスに連携
- **並列タスク実行**: P波ラベリングで50-70%の時間短縮を実現
- **ブラウンフィールドギャップ分析**: 欠落機能と競合の自動検出
- **ビジュアルダッシュボードの提供**: ワークフロー可視化のインタラクティブTUI
- **反復的検証**: 人間のチェックポイントを含むタスクごとの実行
- **8つのAIプラットフォームサポート**: Claude Code、Cursor、VS Code+Copilot、Zed、Windsurf、Codex CLI、Gemini CLI、Qwen Codeで動作

### 解決する課題

**AI支援開発における現在の問題点**:

1. **過剰設計リスク**
   - AIアシスタントがガバナンスなしに複雑なソリューションを生成
   - ベストプラクティス（ライブラリ優先、テスト優先等）の適用なし
   - 技術的負債が急速に蓄積

2. **ブラウンフィールドプロジェクトの課題**
   - 既存コードベースが新しいAI生成要件と競合
   - 欠落機能や競合を検出する自動ギャップ分析がない
   - 手動検証は時間がかかりエラーが発生しやすい

3. **追跡可能性の欠如**
   - 要件 → 設計 → コード → テストの連携が壊れている
   - 仕様への準拠を証明することが困難
   - 判断の理由を追跡することが難しい

4. **逐次実行のボトルネック**
   - AIアシスタントがタスクを1つずつ実行（遅い）
   - 並列化を可能にする依存関係分析がない
   - 独立したタスクを待つ時間のムダ

5. **ワークフロー可視性の低さ**
   - CLIのみのインターフェイスにステータスダッシュボードがない
   - 8つのSDDステージ全体のプロジェクト進捗を見ることが困難
   - エージェント活動のリアルタイム更新がない

6. **プラットフォームロックイン**
   - SDDツールが特定のAIプラットフォームに結び付けられている（例: Claude Codeのみ）
   - Cursor、VS Code+Copilot等を使用するチームはSDDワークフローを利用できない
   - 汎用ソリューションがない

7. **不十分な品質ゲート**
   - AIアシスタントが重要な検証ステップをスキップ
   - 問題を早期に検出する事前承認ゲート（Phase -1 Gates）がない
   - エラーがワークフローステージ全体にカスケード

## 中核機能

### 必須機能（P0 - クリティカル）

MUSUHI 2.0は**8つの中核機能**を提供（すべてP0またはP1優先度）:

#### 1. 憲法ガバナンスシステム（P0）

**ユーザー価値**: 過剰設計を防止、ベストプラクティスを自動的に適用

**9つの不変条項**（spec-kitに触発）:

- **第1条**: ライブラリ優先開発（カスタムコードよりも既存ソリューションを優先）
- **第2条**: テスト優先開発（TDD必須、80%+カバレッジ）
- **第3条**: セキュリティ優先開発（マージ前にセキュリティレビュー）
- **第4条**: ドキュメント優先（実装前に文書化）
- **第5条**: シンプルさ優先（過剰設計を拒否、シンプルなソリューションを優先）
- **第6条**: パフォーマンス優先（パフォーマンス予算の適用）
- **第7条**: アクセシビリティ優先（WCAG 2.1 AAコンプライアンス）
- **第8条**: プライバシー優先（最小限のデータ収集、GDPR準拠）
- **第9条**: オープン優先（デフォルトでオープンソース）

**Phase -1 Gates**: フェーズ承認前にコンプライアンスを検証（バイパス不可）

**期待される影響**: 90%+のベストプラクティス遵守、50%の技術的負債削減

#### 2. 変更ワークフロー管理（P0）

**ユーザー価値**: 変更提案を構造化、ブラウンフィールドプロジェクトをサポート

**2フォルダーモデル**（OpenSpecに触発）:

```
specs/          # 承認済み仕様（安定）
changes/        # 提案された変更（差分形式: ADDED/MODIFIED/REMOVED）
archive/        # 履歴変更（マージまたは拒否）
```

**差分形式**:

- ADDED:新機能/要件
- MODIFIED:［変更前］→［変更後］の変更
- REMOVED:非推奨機能

**ワークフロー**:

1. `changes/YYYY-MM-DD-change-name/`で変更を提案
2. AIが影響分析を生成
3. 人間が承認または拒否
4. `specs/`にマージまたは`archive/`に移動

**期待される影響**: 100%のブラウンフィールドサポート、構造化された変更履歴

#### 3. マルチエージェントオーケストレーション（P0）

**ユーザー価値**: 複雑なワークフローのために20の専門AIエージェントを調整

**20の専門エージェント**:

- **オーケストレーション**: Orchestrator、Steering
- **要件と計画**: Requirements Analyst、Project Manager
- **アーキテクチャと設計**: System Architect、API Designer、Database Schema Designer、UI/UX Designer
- **開発**: Software Developer、Test Engineer
- **品質**: Code Reviewer、Bug Hunter、QA
- **セキュリティとパフォーマンス**: Security Auditor、Performance Optimizer
- **インフラストラクチャ**: DevOps Engineer、Cloud Architect、Database Administrator
- **ドキュメント**: Technical Writer、AI/ML Engineer

**9つのオーケストレーションパターン**（ag2に触発）:

- Sequential Chat（A → B → C）
- Group Chat（マネージャーが次のスピーカーを選択）
- Nested Chat（エージェントがサブエージェントを生成）
- Swarm Pattern（並列実行）
- Finite State Machine（状態駆動遷移）
- Hierarchical（親子ツリー）
- UserProxy（人間参加型）
- Tool Registration（エージェントが関数を呼び出す）
- AutoPattern（自動パターン選択）

**期待される影響**: 手動調整と比較してマルチエージェントワークフローが40%高速化

#### 4. 並列タスク実行（P1）

**ユーザー価値**: 独立したタスクを並列実行（50-70%の時間短縮）

**P波ラベリング**（cc-sddに触発）:

- **P0**: 依存関係なし（最初に並列実行）
- **P1**: P0完了に依存
- **P2**: P1完了に依存

**依存関係グラフ**: DAG（有向非巡回グラフ）と循環依存関係検出

**実行エンジン**:

- タスク依存関係を分析
- P波ラベルを割り当て
- P0タスクを並列実行
- P0完了後にP1タスクを実行
- P1完了後にP2タスクを実行

**期待される影響**: 逐次実行と比較して50-70%の時間短縮

#### 5. ブラウンフィールドギャップ分析（P1）

**ユーザー価値**: 欠落機能、競合、非推奨コードの自動検出

**ギャップタイプ**（cc-sddに触発）:

- **欠落機能**: 実装のない要件
- **競合**: 既存コードが新要件と矛盾
- **非推奨**: 新要件でカバーされていないコード

**ギャップ分析コマンド**: `/musuhi:validate-gap`

**出力**: `gap-report.md`には以下が含まれます:

- カバレッジメトリクス（実装済み要件の%）
- 欠落機能リスト（優先順位付き）
- 競合リスト（推奨される解決策付き）
- 非推奨コードリスト（削除安全性分析）
- 移行計画（P波ラベル付きタスク）

**期待される影響**: ドリフトの削減、ブラウンフィールド移行の高速化

#### 6. インタラクティブダッシュボード（P1）

**ユーザー価値**: ビジュアルワークフロー管理（50%のUX改善）

**TUIダッシュボード**（OpenSpecに触発）:

- **起動**: `musuhi view`コマンド
- **リアルタイム更新**: イベント駆動（手動更新不要）
- **ワークフロー可視化**: 8ステージSDDワークフローで現在のステージを強調表示
- **タスク進捗**: ステータス、担当者、依存関係、P波レベル
- **変更追跡**: `changes/`ディレクトリの保留中の変更
- **ギャップレポート**: 欠落機能、競合、カバレッジメトリクス
- **キーボードナビゲーション**: 矢印キー、Tab、Enter、ESC
- **テーマカスタマイズ**: `musuhi.config.json`
- **エクスポート**: HTML/PDF/JSONレポート

**期待される影響**: 50%のUX改善、ステータス理解の高速化

#### 7. 反復的検証（P2）

**ユーザー価値**: タスクごとの検証による早期エラー検出（40%早い）

**タスクごとモード**（ai-dev-tasksに触発）:

1. **タスクプレビュー**: 説明、期待される出力、依存関係
2. **人間の承認**: 承認、スキップ、または変更
3. **実行**: AIが承認されたタスクを実行
4. **実行後検証**: コード、テスト結果、警告を含む要約

## 製品原則

### 設計原則

1. **仕様優先、常に**
   - 承認された仕様なしにコードを生成しない
   - Phase -1 Gatesを適用（バイパス不可）
   - 追跡可能性は必須（要件 ↔ 設計 ↔ コード ↔ テスト）

2. **プラットフォーム非依存コア**
   - コアSDDロジックはすべての8つのAIプラットフォームで動作
   - プラットフォームアダプターがプラットフォーム固有の統合を処理
   - ベンダーロックインなし（ユーザーはいつでもプラットフォームを切り替え可能）

3. **ドキュメント駆動、データベース駆動ではない**
   - すべての仕様はMarkdown/YAMLファイル（人間が読める）
   - バージョン管理フレンドリー（Gitワークフロー）
   - データベース不要（ファイルベースストレージ）

4. **EARS要件、例外なし**
   - すべての要件がEARS形式を使用（5パターン）
   - 100% EARSコンプライアンス適用（Phase -1 Gate検証）
   - テスト可能性は必須（3:1テスト対要件比）

5. **憲法ガバナンス、不変**
   - 9つの条項はバイパス不可（読み取り専用ファイル権限）
   - Phase -1 Gatesがコンプライアンスを自動的に適用
   - 人間のみの憲法編集（AIオーバーライドなし）

6. **自動化よりも透明性**
   - AIエージェントが何をしているかを表示（ダッシュボードリアルタイム更新）
   - 判断を説明（追跡可能性マトリクス）
   - 人間のオーバーライドを許可（UserProxyエージェントパターン）

### 開発優先順位

**トレードオフを行う場合**:

1. **正確性 > スピード**
   - 速いが間違っているよりも、遅くても正しいソリューションを提供する方が良い
   - Phase -1 Gatesは開発を遅くする可能性があるが、コストのかかるやり直しを防ぐ

2. **追跡可能性 > 利便性**
   - 手動の努力が必要でも要件 ↔ コードの連携を維持
   - 監査コンプライアンスはエンタープライズユーザーにとって交渉不可

3. **シンプルさ > 機能**
   - 過剰設計を拒否（第5条）
   - カスタムコードよりも既存ライブラリを優先（第1条）

4. **テスト可能性 > カバレッジ**
   - 意味のあるテストで80%カバレッジ > 些細なテストで100%カバレッジ
   - 3:1テスト対要件比が品質を保証

5. **プライバシー > テレメトリ**
   - オプトインのみのテレメトリ（第8条: プライバシー優先）
   - PII、テレメトリデータにコード内容なし

**MUSUHI 2.0の優位性**: 憲法ガバナンス、ダッシュボード、20エージェント、マルチプラットフォームサポートを追加

**強み**:

## ドメイン用語

### 主要用語（MUSUHI 2.0全体で標準）

**プロジェクト構造**:

- **ステアリングファイル**: プロジェクトメモリ（structure.md、tech.md、product.md、constitution.md）
- **specs/**: 承認済み仕様（安定、承認後は読み取り専用）
- **changes/**: 提案された変更（差分形式: ADDED/MODIFIED/REMOVED）
- **archive/**: 履歴変更（マージまたは拒否）

**要件**:

- **EARS**: Easy Approach to Requirements Syntax（5パターン）
- **受け入れ基準（AC）**: テスト可能な要件（例: AC-1.1）
- **非機能要件（NFR）**: パフォーマンス、セキュリティ、ユーザビリティ等
- **要件ID**: AC-X.Y形式（例: AC-1.1 = 機能1、基準1）

**ワークフロー**:

- **8ステージSDDワークフロー**: Research → Requirements → Design → Tasks → Implementation → Testing → Deployment → Monitoring
- **Phase -1 Gate**: 事前承認検証（憲法コンプライアンス、EARS形式、追跡可能性）
- **品質ゲート**: フェーズ遷移チェックポイント（成果物完了、ステークホルダー承認）

**エージェント**:

- **エージェント**: 専門AIアシスタント（例: Requirements Analyst、System Architect）
- **Orchestrator**: マルチエージェントワークフローのマスターコーディネーター
- **オーケストレーションパターン**: エージェント通信パターン（Sequential、Group、Nested、Swarm等）
- **エージェントコンテキスト**: エージェント呼び出しの入力データ（ステアリングファイル、前フェーズ成果物）

**並列実行**:

- **P波**: 依存関係レベル（P0 = 依存関係なし、P1 = P0に依存、P2 = P1に依存）
- **DAG**: 有向非巡回グラフ（タスク依存関係の可視化）
- **タスク**: 作業の原子単位（例: "AC-1.1を実装"）

**憲法ガバナンス**:

- **憲法**: 9つの不変条項を含むsteering/constitution.mdのファイル
- **条項**: 憲法原則（例: 第1条: ライブラリ優先開発）
- **Phase -1 Gate**: 承認前の検証（憲法コンプライアンスを適用）

**ギャップ分析**:

- **ギャップレポート**: 欠落機能、競合、非推奨コードをリストする文書
- **カバレッジ**: 実装された要件の%
- **欠落機能**: 実装のない要件
- **競合**: 既存コードが新要件と矛盾
- **非推奨**: 新要件でカバーされていないコード

**追跡可能性**:

- **追跡可能性マトリクス**: 要件 ↔ 設計 ↔ タスク ↔ コード ↔ テストをマッピングする文書
- **追跡可能性チェーン**: Research Finding → Requirement → Design → Task → Code → Test

### 避けるべき用語（混乱または曖昧）

**言わない** → **代わりに言う**:

- "チケット" → "要件"または"タスク"
- "スプリント" → "イテレーション"または"フェーズ"
- "ストーリー" → "ユーザーストーリー"または"要件"
- "エピック" → "機能"または"機能エリア"
- "オーナー" → "担当者"または"エージェント"
- "リソース"（人に対して）→ "開発者"または"チームメンバー"
- "スペック"（曖昧）→ "仕様"または"要件文書"

## コンプライアンスと規制

**MUSUHI 2.0はローカルCLIツール**（クラウドサービスなし、データ収集なし）

### プライバシーコンプライアンス（第8条: プライバシー優先）

**GDPR準拠**:

- PII収集なし（ユーザー追跡なし）
- オプションのテレメトリ（オプトインのみ、匿名化）
- ローカルファイルストレージ（クラウド同期なし）
- ユーザーがすべてのデータを制御（いつでも削除可能）

**CCPA準拠**（カリフォルニアユーザー）:

- 個人情報の販売なし（データ収集なし）
- 透明性（オープンソース、監査可能）

### セキュリティ（第3条: セキュリティ優先）

**ファイルシステムセキュリティ**:

- 読み取り専用憲法（ファイル権限で適用）
- プロジェクトディレクトリにスコープ（外部アクセスなし）
- 監査ログ（すべてのPhase -1 Gate検証）

**秘密ストレージなし**:

- MUSUHI 2.0はAPIキーを保存しない（ユーザーがプラットフォーム設定で管理）
- ステアリングファイルに認証情報なし

### エンタープライズコンプライアンス（ターゲットユーザー: エンタープライズチーム）

**SOC 2 Type II**（監査コンプライアンスを必要とするエンタープライズユーザー向け）:

- 追跡可能性マトリクスが要件 → コード連携を証明
- Phase -1 Gateログが監査証跡を提供
- 憲法コンプライアンスレポート

**ISO 27001**（情報セキュリティ）:

- 第3条（セキュリティ優先）を自動的に適用
- マージ前にセキュリティレビュー（必須）
