## 2. テスト失敗の解決

### 2.1 解決戦略

**目的**: 683/683テスト合格(100%合格率)を達成

**タイムライン**: フェーズ6第1週

**アプローチ**:

1. 根本原因の分析
2. 検出ロジックの修正またはテスト期待値の調整
3. 追加テストケースでの検証
4. 完全なテストスイートの再実行

### 2.2 TEST-FIX-001: Gap Analyzer ConflictDetector

**テストID**: TEST-FIX-001
**優先度**: P1
**担当者**: テストエンジニア + ソフトウェア開発者
**推定作業量**: 2日

#### 2.2.1 失敗テスト詳細

**テストケース**: `ConflictDetector がパターン競合を検出する`

**現在の動作**:

- テストは2つの競合検出を期待
- 実際: 1つの競合が検出された

**期待される動作**:

- 要件が既存のコードパターンと矛盾する場合に競合を検出
- 例: 要件「システムはREST APIを使用すべき」が既存のGraphQL実装と競合

#### 2.2.2 根本原因分析

**調査手順**:

1. テストファイルを読む: `packages/gap-analyzer/__tests__/conflict-detector.test.ts`
2. ConflictDetectorロジックを分析: `packages/gap-analyzer/src/detectors/conflict-detector.ts`
3. 現在のロジックでカバーされていないエッジケースを特定
4. steering/structure.md のパターン定義をレビュー

**疑わしい問題**:

- パターンマッチングロジックが厳密すぎる (部分的な競合を見逃す)
- エッジケースの重要度計算が正しくない
- 複数競合の集約ロジックに欠陥

#### 2.2.3 修正計画

**オプション1: 検出ロジックの改善** (推奨)

- 部分的な競合を検出するためにパターンマッチングを改善
- 重要度計算アルゴリズムを改善
- 競合の重複排除ロジックを追加

**オプション2: テスト期待値の調整**

- 現在の検出限界を文書化
- 現在の機能に合わせてテスト期待値を更新
- 将来の改善のためにTODOコメントを追加

**受け入れ基準**:

- 全85個のgap-analyzerテストが合格 (100%)
- 他のテストでリグレッションなし
- コードカバレッジが80%以上を維持

## 9. リスク評価

### 9.1 高リスク領域

#### リスク1: テスト修正がリグレッションを引き起こす

**確率**: 中 (30%)
**影響**: 高 (合格テストを壊す可能性)

**軽減策**:

- 各修正後に完全なテストスイートを実行

- リグレッションが検出された場合は修正を元に戻す
- 代替修正アプローチを調査

#### リスク2: UATがクリティカルなユーザビリティ問題を明らかにする

**確率**: 中 (40%)
**影響**: 高 (リリース遅延の可能性)

**軽減策**:

- 早期UAT (第2週に2-3人のユーザー)
- 完全なUAT前にクリティカルな問題を修正 (第4週)

**緊急時対応**:

- クリティカルな問題を優先 (P0)
